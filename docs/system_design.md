# 1on1システム 設計書

> イベントストーミング・画面設計をもとにまとめた実装前設計書。
> 最終更新：2026年3月

---

## 1. プロジェクト概要

1on1を管理するシステム。誰でもオーガナイザー（1on1の設定者）にもカウンターパート（1on1の相手方）にもなれる、固定ロールを持たない設計。事前準備・記録（実施・公開・フォローアップ含む）の一連の流れをサポートする。Slack通知を中心としたコミュニケーション連携を含む。

### スコープ（初期実装対象）

- 1on1の一括登録・個別登録（定期・アドホック）
- 事後記録型の1on1（スケジューリングなしで記録のみ作成）
- アジェンダ・事前コメント管理
- 記録（メモ）・アクションアイテム管理
- Slack通知連携
- 記録の公開・閲覧・コメント機能
- ダッシュボード（共通）

### スコープ外（後回し）

- ユーザー登録・ペア管理（初期は最小限の User エンティティ + InMemoryUserRepository で対応）
- 認証・権限管理の詳細実装
- 1on1履歴の一覧・参照画面
- 1on1ペアごとの個別デフォルト公開先設定（Captain 提案で初期対応。必要に応じて後続で追加）

## 2. ユビキタス言語

| 用語 | 説明 |
|---|---|
| **1on1** | オーガナイザーとカウンターパートが実施するミーティング。「セッション」とは呼ばない |
| **オーガナイザー（Organizer）** | 1on1を設定・記録・公開する主体。誰でもオーガナイザーになれる |
| **カウンターパート（Counterpart）** | 1on1の相手方。アジェンダ追加・コメント・アクションアイテム完了を行う |
| **ワークスペース（Workspace）** | 人が集まる単位。再帰的な親子階層を持つ（部署・チーム・プロジェクト等、用途を限定しない） |
| **キャプテン（Captain）** | Workspace の代表者。配下の1on1記録のデフォルト公開先として提案される（自動閲覧ではない） |
| **メンバー（Member）** | Workspace の一般メンバー |
| **メンバーシップ（Membership）** | ユーザーの Workspace への所属。Role（Captain / Member）を持つ |
| **スケジュールグループ（ScheduleGroup）** | 複数カウンターパートへの1on1一括登録・一括管理の単位。オーガナイザーが作成する |
| **アジェンダ** | 1on1で話す予定のトピック一覧 |
| **テンプレートアジェンダ** | スケジュールグループの雛形アジェンダ。各カウンターパートの1on1に展開される |
| **アクションアイテム** | 1on1で決まったタスク。1on1ではなく「人（カウンターパート）」に紐づく |
| **記録（メモ）** | オーガナイザーが1on1中・直後に書く内容 |
| **下書き** | 公開前の状態。オーガナイザーのみ閲覧可 |
| **公開** | 記録をカウンターパートや他の閲覧者に見せる操作 |
| **閲覧者** | オーガナイザーが任意で追加した公開先ユーザー |
| **デフォルト公開先** | Record 公開画面表示時にカウンターパートの所属 Workspace の Captain（祖先含む）から提案される公開先の既定値 |

## 3. ドメイン設計

### 3.1 境界コンテキスト

```
ワークスペース(Workspace) ← 組織・グループの階層管理、所属
        ↓（Captain 情報を提供）
事前準備(Preparation) → 記録(Record)
                                           ↓
                         通知（Slack）← 各フェーズのイベントをトリガーに送信
                         （通知設定も Notification コンテキスト内で管理）

参照（リードモデル）← 全フェーズの結果を蓄積
```

| コンテキスト | 責務 |
|---|---|
| **ワークスペース（Workspace）** | 組織・グループの階層管理、ユーザーの所属（Membership）、Captain / Member のロール管理 |
| **事前準備（Preparation）** | 誰と・いつ会うか（Schedule）、一括登録（ScheduleGroup）、何を話すか（アジェンダ）、事前コメント |
| **記録（Record）** | アジェンダを見ながら進行、メモ、アクションアイテム登録、メモの整理・仕上げ、下書き→公開。公開先設定、コメント・フィードバック、閲覧・振り返り、アクションアイテムのフォローアップを含む |

> **変更の経緯**: 旧構成では4フェーズ（事前準備 → 実施 → 記録 → フォローアップ）に分かれていたが、イベントストーミング v17 の結果、FollowUp コンテキストを Record に統合し3フェーズに再定義した。公開（状態遷移）や公開先設定は Record の属性操作であり、コメントやアクションアイテム完了もドメインロジックが薄く独立コンテキストとしては弱いと判断した。アクターの違い（記録作成はオーガナイザー主体、フォローアップは双方が対等）は Record 内のサブセクションとして表現する。
>
> さらに Session（実施）コンテキストも Record に統合し、3フェーズから2フェーズ（事前準備 → 記録）に再定義した。Session はまだ何も実装されておらず、実施中の操作（アジェンダ確認・メモ・アクションアイテム登録）は Record の責務として扱えるため、独立コンテキストとしては不要と判断した。
>
> **将来の再分離判断基準**: 以下の条件が複数該当する場合、Record からフォローアップを独立コンテキストとして再分離することを検討する。
> - 権限モデルが複雑化し、Record 内での権限管理が煩雑になった場合
> - アクター間の操作差分が拡大し、同一エンティティでの表現が困難になった場合
> - コメント・フィードバックに独自のドメインロジック（承認フロー等）が追加された場合
> - Record コンテキストのコードベースが肥大化し、開発速度に影響が出た場合

### 3.2 登場するアクター

| アクター | 役割 |
|---|---|
| **オーガナイザー** | 1on1を設定・記録・公開する主体 |
| **カウンターパート** | アジェンダ追加・コメント・アクションアイテム完了を行う |
| **閲覧者（Viewer）** | オーガナイザーが公開した記録を読み・コメントできる |
| **キャプテン（Captain）** | Workspace の代表者。Record 公開時にデフォルト Viewer として提案される |
| **システム** | Slack通知などの自動処理 |

### 3.3 コンテキスト間連携（イベントフロー）

| イベント | 発行元 | 消費先 | 説明 |
|---|---|---|---|
| ScheduleCreated | 事前準備 | 通知 | 1on1が設定された時にSlack通知を送信 |
| RecordCreated | 記録 | 参照 | 記録（DRAFT）が作成され、リードモデルを更新 |
| RecordPublished | 記録 | 通知 | 記録が公開された時にSlack通知を送信 |
| AgendaCommentAdded | 事前準備 | 通知 | アジェンダコメント追加時にSlack通知を送信 |
| RecordCommentAdded | 記録 | 通知 | 記録コメント追加時にSlack通知を送信 |
| ActionItemCompleted | 記録 | 参照 | アクションアイテム完了をリードモデルに反映 |
| WorkspaceCreated | ワークスペース | - | Workspace が作成された |
| MemberAdded | ワークスペース | - | メンバー追加（Captain 提案に影響） |
| MemberRemoved | ワークスペース | - | メンバー削除（Captain 提案に影響） |
| MemberRoleChanged | ワークスペース | - | ロール変更（Captain ↔ Member。Captain 提案に影響） |
| WorkspaceHierarchyChanged | ワークスペース | - | 親 Workspace の変更（今後のデフォルト公開先サジェストに影響。過去の Record には影響しない） |

#### コード例（ドメインイベント）

```python
@dataclass(frozen=True)
class ScheduleCreated:
    schedule_id: ScheduleId
    organizer_id: UserId
    counterpart_id: UserId
    scheduled_at: datetime

@dataclass(frozen=True)
class RecordPublished:
    record_id: RecordId
    schedule_id: ScheduleId | None  # 事後記録型の場合はなし
    published_by: UserId
    published_at: datetime
```

## 4. 1on1の3パターン

1on1の開始方法は3パターンあるが、**開始後（記録（実施・公開・フォローアップ含む））の流れは共通**。

### パターンA：一括登録型（スケジュールグループ）

- オーガナイザーがスケジュールグループを作成し、複数カウンターパートに対し1on1を一括登録
- **カウンターパートごとに個別の日時を設定**（1対多の構造）
- 繰り返し設定（Weekly / Biweekly / Monthly 等）はオプション
- テンプレートアジェンダを全カウンターパートに展開（展開後はカウンターパートごとに個別編集可能）
- 一括キャンセル・一括変更（タイトル、共通アジェンダ）が可能

作成起点（3種類）：
1. 新規で作成
2. テンプレートから作成（保存済みテンプレートを参照）
3. 過去の1on1からコピー（履歴を参照）

### パターンB：アドホック相談型

- カウンターパートが相談リクエストを送る
- 日時は**必須**（仮押さえとして登録。オーガナイザー承認で確定）
- カウンターパートがアジェンダを持ち込む

### パターンC：事後記録型

- スケジューリングを経由せず、実施後に記録だけを残す
- 突発的な会話（「5分後にzoomで」等）の記録に対応
- 記録が実施日時と相手を自分で持つ
- スケジュール（予定）には紐づかない

## 5. ドメインイベント一覧

### 事前準備（Preparation）
- スケジュールグループが作成された
- 1on1が設定された（個別 / グループから一括）
- テンプレートアジェンダが作成された
- テンプレートアジェンダがカウンターパートに展開された
- 相談リクエストが送られた
- オーガナイザーが受け付けた
- 1on1の日時が変更された（オーガナイザー・カウンターパートどちらでも）
- 1on1がキャンセルされた（オーガナイザー・カウンターパートどちらでも）
- テンプレートが保存された
- アジェンダが追加された（オーガナイザー・カウンターパートどちらでも）
- アジェンダにコメントが追加された（AgendaCommentAdded。オーガナイザー・カウンターパートどちらでも）
- アジェンダが削除された

### 記録（Record）
- 記録が作成された（RecordCreated。Schedule からの開始 / 事後記録型の直接作成の両方を含む）
- アジェンダが確認済みになった（チェック）
- メモが記録された（記録の箱の中にメモ本文を書き込む。オーガナイザー）
- アクションアイテムが登録された（オーガナイザー）
- ※事後記録型の直接作成も RecordCreated に統一（上記参照）
- 記録が下書き保存された
- 記録が公開された（→ Slack通知トリガー）
- 実際の公開先が変更された
- 記録にコメントが追加された（RecordCommentAdded → Slack通知トリガー）
- アクションアイテムが完了した（カウンターパート）

### 通知（Slack）
- スケジュール通知が送信された（1on1設定時）
- リマインドが送信された（設定時間前・ユーザーごとの設定参照）
- 公開通知が送信された（記録公開時）
- 変更通知が送信された（日時変更・キャンセル時）
- コメント通知が送信された（アジェンダコメント・記録コメント追加時）

### ワークスペース（Workspace）
- Workspace が作成された
- Workspace が更新された（名前変更等）
- Workspace の親が変更された（階層変更。過去の Record には影響しない）
- メンバーが追加された
- メンバーが削除された
- メンバーのロールが変更された（Captain ↔ Member）

### 通知設定
- 通知設定が更新された（ユーザーごと。Notification コンテキスト内で管理）

## 6. リードモデル（参照系）

| リードモデル | 内容 | 主な用途 |
|---|---|---|
| 1on1履歴一覧 | 人ごと・時系列。Viewer として公開された記録のみ閲覧可 | 過去を振り返る・コピー作成の参照元 |
| 未完了アクションアイテム一覧 | 人（カウンターパート）に紐づく | 1on1開始時に「確認しますか？」として表示 |
| 前回の1on1サマリー | ペアごと | 次回アジェンダ作成時の参照 |
| テンプレート一覧 | オーガナイザーごと | テンプレートから1on1作成時の参照 |
| 公開範囲 | ログごと | カウンターパートが「誰に見えているか」確認するため |

## 7. ビジネスルール

### アクションアイテム
- アクションアイテムは**1on1ではなくカウンターパート（人）に紐づく**
- 1on1開始時に未完了アクションアイテムを表示するが、**アジェンダへの追加は任意（強制しない）**
- 一括登録型でもアドホック1on1でも同じ仕組みで動く

### アジェンダ
- オーガナイザー・カウンターパート**どちらでも**追加・削除・コメント可能
- 誰が追加したかのタグを表示（テンプレート / オーガナイザーが追加 / カウンターパートが追加）
- **全アジェンダにコメントを追加できる**（制限なし）
- コメントは全員に公開（非公開コメントなし）

### 公開先
- **オーガナイザーが設定する**（カウンターパートは変更できない）
- **デフォルト公開先サジェスト（Captain 提案）**:
  - Record 公開画面表示時に、カウンターパートの所属 Workspace を起点に祖先 Workspace の Captain を都度計算して提案
  - カウンターパートが複数 Workspace に所属する場合は全所属を対象
  - 重複解消の dedupe key は UserId
  - 「提案」であり「自動閲覧」ではない。オーガナイザーが追加・削除可能
- **Viewer 確定**:
  - 公開実行時にスナップショットとして確定
  - **公開後もオーガナイザーが Viewer を追加・削除可能**
  - Captain でも Viewer に追加されなければ閲覧不可
- **カウンターパートは誰に公開されているかを確認できる**（変更はできない）
- カウンターパート本人には常に公開
- 記録は**公開後にはじめてカウンターパート・閲覧者に見える**（下書き中はオーガナイザーのみ）

### 通知（Slack）
- リマインド時間はユーザーごとに設定可能（通知設定は Notification コンテキスト内で管理）
- コメントが追加されたら通知（アジェンダコメント・記録コメントどちらも）
- 下書き保存時は通知しない。公開時のみ通知する

### ワークスペース（Workspace）
- Workspace は再帰的な親子階層を持つ（深さ制限なし）
- **循環参照禁止**（親を辿っていって自分自身に到達してはならない）
- 親 Workspace の変更は可能。過去の Record には影響しない（今後のデフォルト公開先サジェストが変わるだけ）
- 1つの Workspace に Captain は複数人設定可能
- ユーザーは複数の Workspace に所属可能

### スケジュールと記録の関係
- **スケジュール = 予定**、**記録 = 実施の事実**。別のサブドメインであり独立して存在できる
- スケジューリングされても実施されなければ記録は存在しない（キャンセル等）
- 記録はスケジュールなしでも作成できる（事後記録型：パターンC）
- 記録は実施日時を自分で持つ。スケジュールの予定日時とは異なる場合がある
- スケジュールに紐づく記録は `schedule_id` で参照する（任意）

### Schedule のステータス遷移

```
REQUESTED → CONFIRMED → CANCELLED
    ↑            |
    └────────────┘  （日時変更で REQUESTED に戻る）
```

- **REQUESTED**: 作成直後の状態。相手方の確認待ち
- **CONFIRMED**: 相手方が確認済み。実施予定として確定
- **CANCELLED**: キャンセル済み。不可逆（再作成で対応）

#### 作成時
- Schedule は作成パターン（一括登録・個別作成・アドホック相談）を問わず、常に **REQUESTED** 状態で作成される

#### 日時変更
- オーガナイザー・カウンターパート**どちらでも**変更可能
- 日時変更時はステータスが **REQUESTED に戻る**（再度相手方の確認が必要）
- REQUESTED 状態からの日時変更は REQUESTED のまま
- 変更時はSlack通知を送信
- 通常の日時変更は ConfirmationRequest を使わず直接適用する（ConfirmationRequest はアドホック相談 #79 専用）

#### キャンセル
- オーガナイザー・カウンターパート**どちらでも**キャンセル可能
- キャンセルは不可逆。再度スケジューリングしたい場合は新規作成で対応
- キャンセル時はSlack通知を送信
