# Issue レビュースキル

指定された GitHub Issue を読み込み、コードベースを深く調査して技術設計レビューを行う。

## 手順

### 1. Issue の取得

`gh issue view $ARGUMENTS` で Issue の内容を取得する。
URL が渡された場合はそのまま使用し、番号が渡された場合は `gh issue view <番号>` を実行する。

以下を読み取る:
- 概要（何を、なぜやるか）
- 完了条件（チェックリスト）
- 技術メモ（影響するファイル・モジュール、注意点）
- 関連 Issue / PR

### 2. コードベースの調査

Issue の内容をもとに、以下を徹底的に調査する:

- **関連ファイル・モジュールの特定**: Issue で言及されているファイル、および影響を受けるファイルを洗い出す（`backend/contexts/` 配下の Python ファイル、`frontend/src/` 配下の TypeScript ファイル）
- **既存の設計パターン**: 関連モジュールがどのような設計パターンで実装されているか確認する（DDD レイヤー構成、API設計、コンポーネント構成など）
- **依存関係の把握**: 変更対象が他のモジュールからどう参照されているか（`find_referencing_symbols` 等を活用）
- **テストの現状**: 関連するテストファイルの有無と内容を確認する（pytest / Vitest）
- **パッケージ・設定**: 変更に伴い `pyproject.toml` や `package.json` の依存追加、Docker設定の更新が必要か確認する

### 3. 技術設計レビューの出力

以下のフォーマットでレポートを出力する:

```markdown
## 技術設計レビュー: #<Issue番号> <タイトル>

### 影響範囲
変更が必要なファイル・モジュールの一覧と、各ファイルでどのような変更が必要かの概要。

### 設計方針
推奨するアーキテクチャ・設計パターンとその根拠。
既存のコードベースとの一貫性を重視する。

### 代替案
他に取りうるアプローチとそれぞれのトレードオフ。

### リスク・懸念点
- 破壊的変更の有無
- パフォーマンスへの影響（N+1クエリ、不要な再レンダリングなど）
- 境界コンテキスト間の依存が増えないか
- 既存設計との整合性

### 依存関係
先に解決すべき Issue や前提条件。

### 未解決の設計判断
Issue の記述だけでは決められない技術的選択肢。
ユーザーまたはチームの判断が必要な項目。

### まとめ
Issue の実現に向けた総合判断を簡潔に書く。以下の2点を明確に分けて記載すること:
- **Issue 自体の問題**: Issue の記述に矛盾・情報不足・曖昧さがあり、着手前に Issue の修正が必要な場合はその旨を明記する。問題がなければ「Issue の記述に問題なし」と書く。
- **作業の見通し**: 実装の難易度・作業量・注意点などを端的にまとめる。
```

## 注意事項

- レポートは事実ベースで記述する。コードを読んで確認した内容のみを記載し、推測は明示する。
- 完了条件が曖昧な場合は、その旨をレポートに含める。
- Issue の粒度が大きすぎる場合は、分割の提案も含める。
