# GitHub Issue 作成スキル

ユーザーの要件をもとに GitHub Issue を作成する。

## 手順

### 0. 要件のヒアリング

**`$ARGUMENTS` が空、または曖昧な場合は、issue を作る前に必ずユーザーに質問する。**
推測で issue を作らないこと。

#### $ARGUMENTS が空の場合

以下を順に質問して要件を固める:

1. **何をしたいか**: どんな機能追加・修正・改善か
2. **なぜやるか**: 背景や動機（ユーザー体験の改善、バグ、技術的負債など）
3. **期待する振る舞い**: 完了後にどうなっていてほしいか

一度にすべてを聞かず、回答に応じて深掘りする。

#### $ARGUMENTS がある場合でも、以下が不明確なら質問する

- **スコープ**: 「認証機能を追加」→ ログイン? サインアップ? パスワードリセット? 全部?
- **対象**: 「バグを修正」→ どの画面? どの操作で再現する?
- **優先度・制約**: 既存の仕様との整合性、破壊的変更の許容範囲
- **技術的な選択**: 複数のアプローチがあり得る場合、ユーザーの意向を確認

質問は具体的に、選択肢を提示する形が望ましい。
コードベースを調査して得た情報を質問に含めると、ユーザーが答えやすくなる。

### 1. 要件の分析

- ヒアリングで確定した要件を分析する
- コードベースを確認し、影響範囲を把握する
- 1つの issue が **1つの feature ブランチで完結する粒度** になるよう分解する

### 2. Issue の構成

各 issue は以下のフォーマットで作成する:

**タイトル**: `[カテゴリ] 簡潔な説明` 形式
- カテゴリ: `feat`, `fix`, `refactor`, `docs`, `test`, `chore` のいずれか

**本文テンプレート**:

```markdown
## 概要
<!-- 何を、なぜやるのか。1-3文で。 -->

## 完了条件
<!-- チェックリスト形式で。これが全て満たされたら close できる。 -->
- [ ] ...

## 技術メモ
<!-- 実装のヒント。影響するファイル・モジュール、注意点など。省略可。 -->

## 関連
<!-- 関連 issue、PR、ドキュメントへのリンク。なければ省略。 -->
```

**ラベル**: 以下から適切なものを選択
- `enhancement`: 新機能・機能追加
- `bug`: バグ修正
- `documentation`: ドキュメント
- `good first issue`: 小さく簡単なタスク

### 3. ユーザーへの提示

作成する issue の内容（タイトル・本文・ラベル）を **すべて提示** し、ユーザーの承認を待つ。
複数 issue に分解した場合は、一覧で提示し依存関係も説明する。

**絶対にユーザーの承認なしに `gh issue create` を実行しない。**

### 4. Issue 作成

承認後、`gh issue create` で作成する。複数 issue の場合は順番に作成し、issue 番号を報告する。
issueは日本語で書くこと

## 粒度のガイドライン

- **1 issue = 1 feature ブランチ = 1 PR** が原則
- ブランチ名は `feature/<issue番号>-<説明>` になることを意識する
- 大きすぎる要件は以下の観点で分解する:
  - モジュール境界（例: モデル定義 / API層 / テスト）
  - 依存関係（先に作るべきものを別 issue に）
  - レビューしやすいサイズ（目安: diff 300行以内）
